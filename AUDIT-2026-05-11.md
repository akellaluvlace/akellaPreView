## HIGH bugs SHIPPED (all fixed)

### H1 — Variant-prefixed colour classes silently survive strip pass
**File**: `lib/vibe-edit/style-to-class.ts:42-43` (pre-fix).
**Symptom**: User has `text-blue-500 hover:text-red-500`, picks a new colour from the vibe-edit picker → new `text-[#hex]` lands but `hover:text-red-500` survives → on hover the user sees the OLD red colour, not the new pick. Same for `md:`, `dark:`, `group-hover:`, and chained variants like `md:hover:`.
**Root cause**: `colorMatch("text", "")` from `tailwind-slider-maps.ts` anchors at `^text-…` with no allowance for leading variant prefixes — by design, since it's built for the FocusEditor's per-breakpoint flow. The vibe-edit picker is unprefixed (no breakpoint UI in v1) and needs to strip ALL variants.
**Fix**: Replaced the import-and-use with a local `colorVariantMatcher` that allows `(?:[\w-]+:)*` leading prefix segments. Same broadening applied to `ROUNDED_MATCH`. Also adds `(?:\/[0-9]+)?` for opacity-slashed forms (`text-red-500/50`) that the original regex didn't match either.
**Tests added**: 8 new cases in `tests/vibe-edit-style-to-class-prod.test.ts` covering `hover:`, `md:`, chained `md:hover:`, hyphenated `group-hover:`, prefixed bg + radius, prefix-preserving for non-color classes, opacity-slash forms.

### PX1 / PX7 / SF-H1 — Pixabay XSS via attribution comment + alt fallback
**Files**: `lib/asset-library/insert-pixabay.ts:50-65` (pre-fix).
**Symptom**: A Pixabay user with a malicious display name (e.g. `evil --><script>alert(1)</script><!--`) could inject arbitrary HTML into the user's source code via the attribution comment in HTML mode. Same vector in JSX mode via `*/}`. Plus quote-injection in the `alt="…"` fallback path.
**Root cause**: Photographer name + profile URL + page URL interpolated verbatim into the comment. The alt-text fallback (`Photo by ${name} on Pixabay`) bypassed the tags-only quote escape on line 31.
**Fix**: Added `sanitizeForComment` (strips `-->`, `<!--`, `*/`, `/*`, collapses `--`, strips `<>`, caps 200 chars) and `sanitizeForAttr` (strips `"`, `<>`, caps 200 chars). Applied at the join sites. Author-name alt fallback now sanitizes through `sanitizeForAttr`. Tags-path simplified to use the same helper.
**Tests added**: 6 new cases in `tests/insert-pixabay-prod.test.ts` for HTML `-->` strip, JSX `*/` strip, `<>` strip, `--` collapse, name length cap, and the empty-name fallback (`"Photo on Pixabay"`).

### SF-H3 — Pixabay route may leak `PIXABAY_API_KEY` via error message
**File**: `app/api/assets/pixabay/route.ts:99-100` (pre-fix).
**Symptom**: On fetch failure the route returned `{ detail: String(e) }`. Node's undici fetch error message format may include the offending URL with full query string — and `key=PIXABAY_KEY` is in the query string. A DNS failure or network blip would leak the API key to the client's response body.
**Root cause**: Reflexive `String(e)` on a network error without sanitizing.
**Fix**: Replaced `detail: String(e)` with a static string (`"Could not reach Pixabay — check your network connection."`). Real error logged server-side via `console.error` for debugging. Same pattern applied to the new `res.json()` defensive try/catch for non-JSON responses.

### SF-M7 — Pixabay route 400 fall-through double-consumed response body
**File**: `app/api/assets/pixabay/route.ts:105-114` (pre-fix).
**Symptom**: When Pixabay returned 400 for a reason other than "invalid api key" (e.g. bad `q` param), the 400-branch consumed the body via `res.text()` but didn't return. Control fell through to `if (!res.ok)` → 502, then the success path's `await res.json()` threw on the already-consumed body → generic 500 to client.
**Fix**: 400-branch now always returns — either 401 (invalid-key match) or 400 with bounded `text.slice(0, 200)` detail. Plus a defensive try/catch around `res.json()` for non-JSON upstream responses (Cloudflare challenge, etc.) returning `{ error: "upstream-malformed" }` 502.

### UI1 + UI5 — `code` in dep array reset idle-commit timer + recreated swap callbacks on every keystroke
**File**: `components/Workspace.tsx:2664-2688, 2734-2819` (pre-fix).
**Symptom**: While a vibe element is selected, every Monaco keystroke caused (a) the 600ms idle-commit `useEffect` to re-run, clearing the pending setTimeout and starting a new 600ms wait — meaning vibe drift never committed if the user was also typing in Monaco; (b) `handleVibeOuterSwap` to recreate via `useCallback`, losing referential stability.
**Root cause**: `[vibeInfo, code, kind, setCodeSilent]` dep arrays.
**Fix**: Added `codeRef: useRef<string>("")` + a sync `useEffect([code])` that mirrors `code → codeRef.current` on every render. Both the idle-commit setTimeout and `handleVibeOuterSwap` now read `codeRef.current` and dropped `code` from their dep arrays. Same ref-on-write pattern already used elsewhere in Workspace (`previewHandleRef`, `lastVibeCommitRef`).

### UI3 — Swap modal stayed open across selection changes (stale-target swap)
**File**: `components/Workspace.tsx:2550-2552` (pre-fix).
**Symptom**: User opens icon library while element A is selected, clicks element B (different icon) on the canvas, picks an icon from the library → swap mutates element B (target read from `vibeInfo` closure), not the originally-intended element A. UX confusion.
**Fix**: `handleVibeSelected` now compares `prev.path !== info.path` and closes both `vibeIconSwapOpen` / `vibeImageSwapOpen` on a path-changing selection. The vibe runtime's own re-emits after our direct mutations carry the same path, so this only fires on genuine user-driven selection changes.

### GP1 — Our Picks broken by "List" view-mode override
**File**: `components/GalleryView.tsx:315-320` (pre-fix).
**Symptom**: When picks is the active filter and user switches to List view, `ListView` rendered the 18 picks in a 4-column responsive grid — destroying the 1D curated editorial read order.
**Fix**: Render-priority gate now `viewMode === "list" && activeFilter?.kind !== "picks"`. Picks always falls through to `StaticTemplateGrid` (matches the marquee guard pattern).

### GP2 — Sort dropdown silently no-op on picks (no visible disable)
**File**: `components/GalleryView.tsx:249, 482-510` (pre-fix).
**Symptom**: Picks's filter memo short-circuits to curated order regardless of `sort` value. User toggling "Sort · A → Z" while on picks sees nothing change, with no UI signal that the dropdown is inert.
**Fix**: Added `disabled` + `title` props to `SortSelect` + `ViewSelect`. Both visibly disable with `opacity-50 cursor-not-allowed` + tooltip `"Sort is fixed to the curated order for Our picks"` / `"View mode is fixed to the curated grid for Our picks"`.

### UI4 — TextTypographyExtras slider overwrote arbitrary-value classes
**File**: `components/VibePropertiesPanel/TextTypographyExtras.tsx:109-144` (pre-fix).
**Symptom**: `detectTypographyProps` matches by regex (broad), `currentIndex` looks up exact scale match (narrow). Mismatch case: element has `text-[12px]` (arbitrary). `detectTypographyProps.fontSize === true`, slider renders. `currentIndex === -1`, slider value defaults to 0. User drags the slider one notch → `setScale(tokens, FONT_SIZE, 0)` replaces `text-[12px]` with `text-xs` silently — custom value lost with no warning.
**Fix**: When `idx < 0` (arbitrary value detected), slider renders disabled + greyed (opacity-40) with title `"Remove the custom value (×) to use the scale slider"`. The × remove button always renders (was previously gated on `idx >= 0`) so users can escape an arbitrary value back to slider-edit mode. Display label changes from `"—"` to `"custom"`.

## MED bugs SHIPPED (fixed)

### M2 — `patchJsxOuterByOid` lost OID continuity when asset markup carried a foreign OID
**File**: `lib/ast/patch-class-by-oid.ts:390-401` (pre-fix), plus mirror at `lib/vibe-edit/runtime.ts:308`.
**Symptom**: If an asset (library item, pre-stamped export) ships with `data-dropin-id="foreign-asset-99"`, `injectOidIntoOuter` early-bailed and left the foreign OID in place — the target element's OID is now gone, and subsequent vibe-edit ops on this element by its original OID fail to resolve silently.
**Fix**: Strip any existing `data-dropin-id="..."` / `'...'` attr from `newOuter` BEFORE injecting the target's OID. Both server-side (patcher) and runtime-side (iframe char-scan) hardened. Single-quote variant also handled.
**Tests added**: 2 new cases in `tests/patch-by-oid-prod.test.ts` (`"replaces a FOREIGN OID in newOuter with the caller-supplied OID"`, `"strips single-quoted foreign OID variant too"`).

### WU6 — OID char-scan stalled on multi-line asset markup
**File**: `lib/vibe-edit/runtime.ts:318-321` (pre-fix).
**Symptom**: Asset library outputs sometimes format multi-line markup (SVG icon with open tag on its own line). The char-scan whitespace skip only handled space (32) + tab (9) — newline (10) and carriage return (13) stalled the scan before the tag name, OID injection silently no-op'd, swap proceeded without OID continuity.
**Fix**: Extended whitespace skip loop to include LF (10) + CR (13).

### SF-H2 + SF-H4 — Empty catches in iframe runtime swallowed DOM errors
**File**: `lib/vibe-edit/runtime.ts:271, 340` (pre-fix).
**Symptom**: `try { el.outerHTML = stamped } catch (e) {}` and `try { el.style[prop] = v } catch (e) {}` swallowed any DOM exception (CSP nonce mismatch, sandboxed-iframe innerHTML restrictions, parser rejection of malformed asset markup, frozen style on detached element) silently. The runtime still re-emitted `vibe:selected` afterward, so the host's vibeInfo state desynced from real DOM state — next idle commit wrote bad drift to source.
**Fix**: Both catches now `console.warn` with descriptive labels.
